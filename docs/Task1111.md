## Goal

Feed real project screenshots into generated portfolio sites and keep them
current without manually capturing, naming, uploading and deleting each image.
Use stable image slots and one reviewed publishing batch:

`Refresh showcase -> Capture -> Preview -> Publish`

Changing screenshots must not require regenerating the website.

## Agreed approach

1. Capture the selected views locally on this PC. Use stable names such as
   `CMDSTATUS`, `CMDMODELS`, `RECLAIM11_DOOR`, `RECLAIM11_PRO`,
   `RECLAIM11_BEGINNER` and `PHONEDASHBOARD`.
2. Produce readable, web-optimized images, with project-scoped paths such as
   `assets\command-center\CMDSTATUS.webp`. Preserve image dimensions and useful
   descriptions so the gallery can handle both wide desktop and tall mobile
   screenshots.
3. Maintain a small project catalog containing titles, descriptions, cover
   images, screenshot lists and project/source links. Give the client builder
   this catalog and approved local image files; local previews and the
   published site must use the same assets.
4. Stage only changed images and catalog entries. Preview the batch, then
   publish on one explicit operator confirmation.
5. Publish the curated static portfolio through GitHub Pages. Replace files
   at their existing paths, commit and push normally; no manual remote deletion
   or force-push. Use a dedicated publishing checkout, not a bulk upload of the
   GodBrain working tree.
6. Add an automatic content version to image references so browsers fetch
   replacements instead of retaining old cached images. For example:
   `assets/command-center/CMDSTATUS.webp?v=7f42c8`. Stable names remain stable;
   the content version changes when the image changes.

Routine capture, compression, comparison and publication are deterministic
automation. They must not require model calls or AICs.

## Local workflow

From the repository root:

```powershell
.\scripts\Build-Showcase.ps1
.\scripts\Refresh-Showcase.ps1
```

Refresh captures all six views by default. `-Images` selects slots to recapture;
the other named PNGs must already exist. `-SkipCapture` rebuilds from the existing
capture set. Capture/encoding/validation failures do not touch the publishing
checkout. The builder catalog is replaced only after validating the copied
snapshot; failed replacement restores the previous directory.

The default private work root is `godbrain_core\skill_lab\work\gym`. Batches
contain `site\`, `review.json` and a private encoder log. Override
`-BuilderWorkDir`, `-CaptureDirectory` and `-BatchDirectory` when needed.
Public files are only the exact manifest-listed static files under `site\`.

Use a **dedicated clean main checkout** of `autom8edIT/autom8edIT.github.io`:

```powershell
.\scripts\Publish-Showcase.ps1 -BatchDirectory <batch> -PublishingCheckout <checkout>
```

This stages only the curated `projects\` files and one homepage link. It writes
`publishing-review.json`, binding the batch, base commit, exact file bytes and
Git blobs. It also prepares `<batch>\preview` with only the public gallery and
the existing portfolio theme helper. Inspect the staged diff, then use the
printed loopback static-server command and open `/projects/`. Do not serve the
Git checkout or private batch root. This is a gallery preview, not a complete
Jekyll homepage build.

Only after reviewing the sanitized images:

```powershell
.\scripts\Publish-Showcase.ps1 -BatchDirectory <batch> -PublishingCheckout <checkout> `
    -Publish -ApprovedReview <review_sha256>
```

Missing/wrong/stale approval, changed working/index bytes, extra files or an
unexpected repository/branch block publication. Exactly one approved fetch URL
and one approved push URL are required; additional destinations are rejected.
Commit tree/base are checked before ordinary non-force push of the exact approved
commit, and the remote main commit is read back.

The approved tree is persisted before committing and the exact commit before
pushing. An interrupted commit, failed push or failed remote readback leaves a
pending publication, not an unchanged-success receipt. Retry the same `-Publish
-ApprovedReview <review_sha256>` command: it revalidates the original approval,
tree/base, changed paths and working/index bytes, then pushes or confirms that
same commit without creating another. Restaging is blocked while publication
is pending. A confirmed unchanged batch produces no new commit or push. Use one
publisher at a time per dedicated checkout. No automatic publisher or new model
tool was added.

## Safety and acceptance

- Capture only intended views, not the entire desktop. Never click service,
  model-start/stop or Reclaim11 repair controls as part of capture.
- Public output must exclude tokens, credentials, private host details and
  unrelated windows. Review the sanitized batch before publishing.
- GitHub Pages serves the static portfolio and images, not the live control
  panel, local APIs, MongoDB or model listeners.
- Publication is an operator-controlled local workflow, not permission for
  the model/kernel mouth to run `git push`.
- Failed captures must report failure and leave the last good published
  images intact. Unchanged captures should not produce needless commits.
- Confirm that replacing the named images updates both local previews and
  the deployed gallery without a new website generation.
- Preserve manual-only client generation, completed-course idling and the
  one-GPU-slot/host-hold rules.
